A Feature, Not a Rewrite

Most applications don't need to become "AI applications." They need one or two places where a model does something a rule can't.

The model is a dependency, like a database or a payment API: it has latency, it costs money per call, it goes down, and its output needs validating.

Treat it that way and most of the "AI" problems turn into ordinary engineering problems.

This is the thesis. Every later section comes back to "it's a dependency": section 2 handles its failures, section 6 limits what it can do, section 7 measures it.

Choosing a First Feature

Good first features have three things in common:

  • Being wrong is cheap. A bad category suggestion costs a click.
  • A person stays in the loop. The AI suggests and someone chooses whether to accept.
  • A rule genuinely won't do. If a regex works, use the regex.

Start with suggestions. Earn your way to actions.

Quick wins vs. ambitious projects in one line: the fragment. Triage suggestions are a quick win; an assistant that issues refunds on its own is not, and section 6 shows why it shouldn't.

One Call


token_provider = get_bearer_token_provider(
    DefaultAzureCredential(),
    "https://cognitiveservices.azure.com/.default")
client = OpenAI(base_url=ENDPOINT, api_key=token_provider)

response = client.responses.create(
    model=DEPLOYMENT,
    instructions="You are a support agent for a bike shop.",
    input="My back wheel clicks when I coast. Is it safe?",
    reasoning={"effort": "low"},
    max_output_tokens=2000,
)
print(response.output_text)

No API key: az login supplies the identity, and the SDK asks the token provider for a fresh token when it needs one.

This is first_call.py, trimmed. Run it right after this slide or right after the next one; it takes about four seconds. ENDPOINT is https://RESOURCE.openai.azure.com/openai/v1/ -- the resource, not a Foundry project URL. A Foundry resource works with no code changes.

The local-model story, on a slide instead of live. Ollama's OpenAI-compatible endpoint includes the Responses API and strict structured outputs. Local is possible; local is not free.

Deployment Name vs. Model Name

On Azure, model= takes the deployment name: the name you gave the model when you deployed it.

Name the deployment after the model and nobody gets confused. Name it prod-chat and you can swap the model underneath without a code change, but nobody can tell what is answering.

Either way, log response.model. It tells you what actually answered.

Thirty seconds. The fragment is the production habit: every logged call in section 7 records response.model, not the deployment name.

The Controls That Matter Now

  • Model choice: the biggest lever on quality, cost, and latency
  • Reasoning effort: how hard the model thinks before answering
  • Max output tokens: a ceiling, and reasoning tokens count against it
  • Instructions: the system prompt, kept in a versioned file

And the one everyone remembers?

HTTP 400: Unsupported parameter: 'temperature' is not supported with this model.

Run first_call.py --temperature for the second fragment. That error is the real response from the demo deployment. Reasoning models drop sampling parameters. Effort is the dial now. Triage runs at effort "low": it doesn't need deep thought, and every level up costs latency and tokens.

Structured Outputs


class Triage(BaseModel):
    category: Category      # billing, shipping, returns, ...
    priority: Priority      # low, normal, high, urgent
    order_number: str | None
    product: str | None
    sentiment: Sentiment
    summary: str
    needs_human_review: bool

response = client.responses.parse(
    model=DEPLOYMENT, instructions=prompt.text,
    input=f"<ticket>\nSubject: {subject}\n\n{body}\n</ticket>",
    text_format=Triage,
    max_output_tokens=4000,
)
triage = response.output_parsed      # a Triage, not a string

The Pydantic model is the contract: the SDK sends it as a strict JSON schema, and the model can only produce that shape.

No "please respond in JSON," no regex over the output. Point at needs_human_review: it is the "I'm not sure" path, and it is a better design than asking the model for a confidence score, which it will invent. The ticket goes inside ticket tags. That matters in about two minutes.

What an Embedding Is

Text in and a fixed-length list of numbers out: 1,536 of them for text-embedding-3-small.

The numbers are arranged so that texts with similar meaning land close together, whatever words they use.


response = client.embeddings.create(
    model="text-embedding-3-small", input=texts)
vectors = [item.embedding for item in response.data]

Same client as before. A different deployment.

No math. If someone asks how: a model trained so that related text produces nearby vectors. "Nearby" is cosine distance, which is on the next slide but one. One call embeds the whole batch: all 44 tickets went in a single request.

Vectors Live in Your Database


CREATE TABLE ticket_embeddings (
    ticket_id VARCHAR PRIMARY KEY,
    model     VARCHAR NOT NULL,
    embedding FLOAT[1536] NOT NULL
);

SELECT t.ticket_id, t.subject, t.resolution,
       array_cosine_distance(e.embedding, ?::FLOAT[1536])
           AS distance
FROM ticket_embeddings e
JOIN tickets t USING (ticket_id)
ORDER BY distance
LIMIT 3;

This is DuckDB, but PostgreSQL with pgvector and SQL Server 2025 work the same way.

Ordinary SQL against the database the app already has. Point at the model column; it pays off on the production slide. The query returns the resolution, which is what the agent actually wanted: how the last three of these were fixed.

Exact Until It Isn't

That query compares against every vector. At help-desk scale, thousands of tickets, it takes milliseconds.

At millions, use an approximate index:


INSTALL vss;
LOAD vss;
CREATE INDEX ticket_embeddings_hnsw ON ticket_embeddings
    USING HNSW (embedding) WITH (metric = 'cosine');

Using an index trades a little recall for a lot of speed.

Optional live: build_index.py --hnsw shows the same top three and a query plan that uses the index. HNSW persistence in DuckDB is still experimental, so the demo builds it on an in-memory copy. Check the watch list before claiming otherwise.

Change the Model, Re-embed Everything

This index was first built with a local model: 768 dimensions. Then it moved to Azure: 1,536.

The old vectors weren't wrong. They were incomparable, so every ticket was re-embedded.

  • Store the model name on every vector, and refuse to compare across models
  • Distances only mean something within one model: close matches were 0.25 before, 0.45 after
  • Semantic search always returns something: "broken" also finds "Brakes failed on descent"
A real story from building the demos. The matches held up across the switch; the thresholds did not. A cutoff tuned on one model is wrong on the next. The app used to show an empty "Similar tickets" panel after a model switch. Now it says which model the index was built with. Quiet failure is the bug.

The Model Doesn't Know Your Return Policy

Aisha's helmet is too small. She tried it on indoors. Ask the model for a reply with no help:

Yes—you can return the Aero Lid for a refund, since you only tried it on indoors. Please send it back in its original condition…

Wobbly Wheel's actual rule: helmets are returnable only if the retention straps haven't been adjusted. The draft never mentions it.

It sounds right, and nobody can check where it came from.

Run draft_reply.py T-1040 --naive live, or show this slide if time is short. The quote is the real output. The danger isn't nonsense; it's plausible, unsourced, and slightly wrong.

Retrieval-Augmented Generation

  1. Chunk the knowledge base and embed every chunk ahead of time
  2. Retrieve the chunks closest to the ticket
  3. Generate with those chunks in the prompt, numbered, and ask for citations
  4. Check the citations before anyone trusts the draft

Step 2 is free here: the ticket's vector from section 3 lives in the same space as the KB chunks.

Most RAG explanations stop at three steps. The fourth is the production one. The fragment is a nice reuse: same embedding model for tickets and KB means a stored ticket can retrieve KB sections with no API call. The panel shows sources on page load for that reason.

Chunking

Twelve articles become 37 chunks, split at each heading.

  • A KB article is already organized by topic, so a heading is a natural boundary
  • Every chunk keeps its article title: "Returns Policy > E-bikes" still means something on its own
  • The longest chunk is about 500 characters

Chunking is the step people get wrong most often and revisit least.

The general advice: split where the document's own structure splits, keep context with each chunk, and look at your chunks. build_kb_index.py --show lists them. Fixed-size chunks that cut a policy in half are the classic failure.

The Grounding Prompt

Use only the numbered knowledge base sources and the order details you are given. Cite the source for each policy, time frame, or amount in square brackets, like [2].

If the sources do not answer the customer's question, do not guess and do not fill the gap from general knowledge. Write a short reply that acknowledges the question and says a specialist will follow up, and cite nothing.

The grounded draft: the strap rule, the 45-day window, a citation, and "please start the return by November 17," worked out from the delivery date.

From prompts/draft_reply/v1.md. The second paragraph is the permission to say "I don't know," and it matters as much as the first. The fragment is the real T-1040 draft. It also left out the $12 label fee. Correct to its sources, still not perfect: a person edits before anything is sent.

Streaming


with client.responses.stream(model=DEPLOYMENT,
                             instructions=prompt.text,
                             input=context) as stream:
    for event in stream:
        if event.type == "response.output_text.delta":
            yield event.delta
    response = stream.get_final_response()

Streaming doesn't make the answer faster. It makes the wait shorter: first text after about 2 seconds, done after about 3.

The browser gets server-sent events: text as it is written, then the citation check.

In rehearsal, one draft took 53 seconds. Streaming hides the wait only once text starts arriving; it doesn't fix a slow first token.

When a Draft Is Wrong

Check retrieval first. If the right section wasn't retrieved, no prompt can save the answer.

Check the citations. Every [n] must point at a source you actually provided.

Retrieved text is untrusted input. A knowledge base can carry instructions just like a ticket can.

And the "I don't know" path works: asked whether a helmet is MIPS certified, the draft said a specialist would follow up, and cited nothing.

Retrieval for the ticket with three unrelated questions found the price-match section and missed the locked-account one. One query vector can't point three ways.

The Tool Calling Loop


while True:
    response = client.responses.create(
        model=DEPLOYMENT, instructions=prompt.text, tools=TOOLS,
        input=pending, previous_response_id=previous)
    previous = response.id
    calls = [i for i in response.output
             if i.type == "function_call"]
    if not calls:
        return response.output_text     # the model answered
    rounds += 1
    if rounds > MAX_TOOL_ROUNDS:
        return "Stopped."               # a bug, or an attack
    pending = [{"type": "function_call_output",
                "call_id": c.call_id,
                "output": run(c.name, json.loads(c.arguments))}
               for c in calls]

The model never runs anything. It asks and your code decides.

This is run_turn() in assistant.py, compressed. Walk it once: send tools, get calls or an answer, run the calls, send results, repeat, with a cap. previous_response_id means the provider holds the conversation; each request sends only what is new. That convenience has a privacy cost; section 7.

Defining a Tool


{
    "type": "function", "name": "propose_refund",
    "description": "Propose a refund for the agent to approve. "
                   "This does NOT issue the refund.",
    "strict": True,
    "parameters": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string"},   # like WW-10462
            "amount":   {"type": "number"},   # US dollars
            "reason":   {"type": "string"},   # cite the policy
        },
        "required": ["order_id", "amount", "reason"],
        "additionalProperties": False,
    },
}

The description is a prompt. strict guarantees the arguments match the schema but it doesn't make them correct.

Strict mode means you'll get a string and a number. It does not mean the order exists, belongs to this customer, or that the amount is allowed. That's the next slide.

Defense in Depth

  1. The prompt says ticket text is data, not instructions
  2. The tools can only see this customer
  3. Code enforces ownership and refundable amounts
  4. No tool issues a refund
  5. A person approves every proposal
  6. The loop stops after five rounds

The prompt is the only layer the attacker can talk to. That's why it isn't the only layer.

T-1042 results: it answered the MIPS question and flagged the instruction to the agent; refused "do what the ticket says"; and couldn't see another customer's order. If it ever does propose a refund, that's the demo: a proposal waiting for a person, which you reject.

Your History Is Your Eval Set

You can't tell whether a change helped by reading a few outputs.

Every resolved ticket already has the category and priority a person gave it: 36 labeled examples nobody had to build.

Run the prompt over them and score every field. Score the expensive mistake separately: urgent recall, the share of safety tickets caught.

Baseline, prompt v1: category 97%, priority 92%, urgent recall 100%.

Walk one of the four v1 misses. T-1010 is a 2FA problem whose real ask is changing a shipping address; the model said shipping. Is the model wrong, or the label? Labels deserve a second look too.

A Reasonable Change

On-call complains: they get paged for every urgent ticket. Someone edits one line.


- urgent: a safety risk to the rider or to property.
-   Battery swelling, overheating, burning smells,
-   brake failure, cracked frames or forks.
+ urgent: someone has been injured. Reserve urgent for
+   injuries; on-call is paged for every urgent ticket.

It looks like a fix. Ship it?

Prompts are files, so a prompt change is a diff in code review, like any other. Let the room vote before the demo.

Cache Where Inputs Repeat


parts = [prompt.text, chat_model(), reasoning_options(),
         subject, body]
key = hashlib.sha256(
    json.dumps(parts, sort_keys=True).encode()).hexdigest()

Rerunning v1: 0 model calls, 0 tokens, 0.0 seconds. Editing the prompt changes the key, so v2 made 36 fresh calls.

Pays off for evals, repeated queries, and backfills. Live tickets are almost never identical.

Key on everything that can change the answer: the prompt TEXT, not its version name, plus model, reasoning settings, and input. Miss one and you serve stale answers.

Log Every Call


{"ts": "2026-10-17T02:24:21.347+00:00",
 "feature": "triage", "kind": "chat", "prompt": "triage/v1",
 "model": "gpt-6-luna", "input_tokens": 730,

Track each call individually, including successes and failures. DuckDB reads the file directly, though perhaps look at tools like Langfuse to visualize and analyze the logs:

  • Calls, cache hits, and errors per feature and prompt version
  • Latency: triage p50 about 3 seconds, p95 about 10
  • Cost, computed at report time from prices in config
Plan the UI for p95, not p50. Cost isn't stored in the log; it's computed from the price sheet when you report. Fix a wrong price and the whole history is fixed. Prices are Global Standard rates from the public Azure Retail Prices API, pulled 2026-10-16: gpt-6-luna at $0.10 in / $0.50 out per million tokens, text-embedding-3-small at $0.02 per million. No auth, so anyone in the room can check. A full 36-ticket eval run costs about four tenths of a cent. Re-pull before each delivery.

Timeouts, Retries, and Degradation


OpenAI(base_url=ENDPOINT, api_key=token_provider,
       timeout=60, max_retries=3)
  • The SDK defaults are a 10-minute timeout and 2 retries. Neither suits a button a person is waiting on.
  • Retries back off on 429, 5xx, and connection errors
  • Every feature sits behind a flag and an error boundary: when the model is down, the help desk still works
Demo 1 already showed degradation live. This slide just names it.

Models Retire and Data Travels

Models retire. For example, gpt-5-mini retires on 2027-02-09. Pin the version, and rerun the eval before every upgrade.

Prompts are versioned files. That way, you can always know which version was used for each call and evaluation run.

Data travels. Tickets, orders, and conversations go to the provider, and previous_response_id means the provider stores the assistant's conversations. Know your retention settings.

The eval harness is what makes a model upgrade safe: same command, new deployment, compare. Check the retirement date on the watch list before every delivery; it will be out of date eventually.

When to Reach for a Framework

Everything today was the plain SDK, so you could see what happens. Frameworks package these patterns:

  • Microsoft Agent Framework: successor to Semantic Kernel and AutoGen, .NET and Python
  • LangChain and LangGraph: Python and JavaScript
  • Microsoft.Extensions.AI: provider-neutral abstractions for .NET

Reach for one when you're writing the same loop for the third time, not the first.

Re-verify names and status before each delivery; this is the slide most likely to go stale.

Wrapping Up

Key takeaways:

  • Start with one feature, one model, one eval set
  • Get structured output and check the three failures that don't raise
  • Ground generation in your data, cite it, and let it say "I don't know"
  • The model asks and your code decides. Put a person in front of every write.
  • Score more than one number, and gate on the expensive mistake
